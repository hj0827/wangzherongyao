## 2. P0：三件事，都在"改一处要牵一串"的路径上

### 2.1 `arena.gd` 6087 行，已经是铁律 5 的 10 倍

`docs/ai/01-repo-reality.md:85` 写的是 3921 行——**这个数字已经过时**（评审期间它还在涨：5516 → 6003 → 6086 → 6087）。

按函数名前缀实测切分（6086 行版）：

| 分块 | 行数 | 内容 |
| --- | --- | --- |
| 世界构建 `_build_* / _lane_* / _bridge_* / _wall_* / _plaza_* / _rock_*` | 2566 | 地面、三路、河、桥、墙、草坪、野区道具、基地摆件 |
| 运行时 `_process / _gather_input / _update_camera / debug_*` | 1752 | 主循环、键鼠与触控、相机、调参 |
| 表现同步 `_sync_* / _handle_* / _process_events` | 619 | 快照→视图、事件→特效 |
| 特效与池 `_spawn_* / _update_decals / _init_vfx_pools` | 740 | 飘字、粒子、刀光、弹道、残留 |

`_process()` 一个函数 144 行，里面同时干：网络 poll → 音频上下文 → 顿帧判定 → 输入采集 → 30Hz 补帧 tick → 快照构建 → 事件消费 → 网络广播 → 视图同步 → 相机 → HUD。**这个函数无法单测，只能靠真机看。**

**为什么一直没人拆（真正成本）**：`godot/tests/` 里有 **53 处** `FileAccess.get_file_as_string(...)` 直接 grep 源码字符串，其中 **24 处断言的是 `arena.gd` 本身**（分布在 19 个测试文件里）。一拆文件，这些用例立刻一片红——但红的原因不是功能坏了，是"字符串搬家了"。这就是拆不动的根因。

**建议顺序**（先拆最不容易被源码断言绑住的部分）：

1. `arena_world_builder.gd`：把 2566 行的世界构建整块搬出去，`Arena` 只留一次调用。这块与战局运行时不共享状态，风险最低。
2. `arena_fx_factory.gd`：`_init_vfx_pools` + `_spawn_damage_number / _spawn_particles / _spawn_ring / _spawn_slash / _spawn_tracer / _spawn_lance / _spawn_trail / _spawn_decal`（池 + 复用），硬规则 4 的守卫集中在一处。
3. 剩下的 `Arena`（≈1700~2000 行）才谈 `_process` 分段。

**拆分前的必做前置**：把那 24 处源码字符串断言改成「断言新模块的公开静态函数」。这是净收益——把"文件里有这行字"变成"这个函数真的存在且行为正确"。

### 2.2 事件类型是裸字符串，没有任何共享契约

- `match_sim` 侧 `_emit("...")` 实测 **32 种**类型；
- `arena._process_events()` 的 `match` 实测 **47 个分支**；
- 两边**没有共享枚举或常量表**（`grep EVENT_TYPES|const EVENTS|enum Event` 为 0）。

后果：拼错一个字母 = 事件静默丢了。表现是"这个技能没特效/没播报"，不报错、测试也不红——和硬规则 5、6 是同一类坑，只是这次在事件名上。

**建议**：新建 `sim/event_types.gd`（纯常量，`RefCounted`），sim 只 `_emit(EVT.SKILL, ...)`，arena 只 `match type: EVT.SKILL`。再加一条用例：把 arena 源码里出现的所有 `"xxx"` match 分支与常量表比对，**多一个少一个都红**。成本约 1 小时，收益是永久的。

## 3. P1：把"靠人记的清单"变成"靠测试的清单"

### 3.1 英雄字段：snapshot 与白名单已对齐，但有一处真实漏网 + 43 个沉默字段

实测（探针 `godot/.tmp/probe_schema_parity.gd`，过程文件，不入库）：

- `_spawn_hero()` 106 个键 → `_snapshot_entity()` 88 个 → `sanitize_snapshot` 88 个，英雄侧**零丢失**；
- 但结构物侧有一处真实漏网：`guard` 实体在快照里带 `lane`，`_sanitize_entity` 的 `elif type == "guard"` 分支（`godot/net/net_protocol.gd:542`）没放行它，**客机拿不到 `lane`**。当前表现层没读这个字段，所以没暴露——正是"加字段漏一处、单机正常"的原型；
- 另有 **43 个 spawn 键从不进快照**：`attack_damage / attack_range / attack_interval / base_* / assists / damage_dealt / tower_kills / attack_mode / locked_target / gold_fraction / passive_stacks / cc_immune_timer / shield_timer / path_*`。

其中大部分是合理的（视图用 `HeroDefs` 拿射程，不重复下发）。`cc_immune_timer` 属于"故意不下发"这一档——它的读取点只有 `sim/control_rules.gd:65`（`test_cc.gd:473` 专门守这条），客机靠快照里的 `cc_status` 状态码显示，不需要原始计时器。**结论正确，但代码里没有任何一处写明"这是故意的"**，与"忘了加"长得一模一样。

**建议**：把探针固化成一条用例 `test_schema_parity.gd`，断言 snapshot 键集 ⊆ 白名单键集（这条现在恒真，但能锁住未来），并把"故意不下发的字段"写成显式白名单，避免"忘了"和"故意"长得一样。

### 3.2 三份几何知识、三份队伍色

| 知识 | 现状 |
| --- | --- |

| 队伍色 | `arena.BLUE = (0.22,0.6,1.0)`、`unit_visual.BLUE` 同值、`game_theme.BLUE = (0.24,0.62,1.0)`（不一致）；GOLD 三处 `(1.0,0.8,0.38)` / `(1.0,0.78,0.32)` / `(0.84,0.66,0.34)` |

队伍色不一致不一定是 bug（UI 主题色与 3D 特效色本就该分层），但**现在没有任何注释/测试说明这是故意的**，下一个人会当 bug 改。建议 `GameTheme` 里区分 `TEAM_BLUE_UI` 与 `TEAM_BLUE_VFX`，或在 3D 侧统一引用一份。

### 3.3 测试稳定性：`test_net_session` 是真时钟驱动

- 全量跑第 1 次：`test_team_snapshot_broadcast_filters_each_team -> guest received one team snapshot (expected 1, got 0)` 红；
- 单跑 3 次：全绿；之后全量 2 次：全绿。
- 原因：`_pump()` 用 `OS.delay_msec(5)` + `Time.get_ticks_msec()` 等真实时间，`_pump` 默认等 2 秒，22 次调用。

**这是 flaky，不是功能坏**——但它会让人误判"我刚改的东西坏了"。另外 `test_net_session` 单文件 41.7s，全套 162s，靠"跑全套"来验证一个改动太慢。

**建议**：`_pump` 改为只 `poll()` 不 sleep，或把 session 的计时改成可注入的时钟；同时把 `.tmp/run_one.gd` 这类单文件跑法固化成正式工具（现在它在被 ignore 的目录里）。

## 6. 一句话回答"需不需要优化"

**需要，但不是重构。** 这个仓库的分层纪律（sim 纯逻辑 / view 只读 / 协议白名单）是守住的，这是最难的部分。真正在漏的是三样：**一个 6000 行的表现层入口**、**一批靠人记的裸字符串契约（事件名、字段清单、输入键）**、**一个已经被测试养着但生产不用的模块**。这三样都不需要改架构，只需要持续做减法。
